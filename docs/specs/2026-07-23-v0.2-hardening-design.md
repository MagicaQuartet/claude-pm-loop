# Design: v0.2 hardening — deterministic guardrails, review-cost scaling, reviewer diversity, knowledge hygiene

- **Date:** 2026-07-23
- **Status:** Draft — direction approved in brainstorming (2026-07-23); awaiting spec review before the implementation plan
- **Author:** Dongseong Kim (with Claude Code)
- **Repo:** `claude-pm-loop` (builds on the v0.1 extraction design, `2026-07-23-pm-loop-plugin-extraction-design.md`)

## 1. Goal

An objective post-v0.1 review identified four structural weaknesses. This design fixes them
without changing the loop's shape (stages, roles, and the human merge gate all stay):

- **W1 — Deterministic guardrail.** The entire control plane is prose; the merge gate has no
  hard backstop. Ship a plugin `PreToolUse` hook that forces a harness prompt to the human at
  the moment a merge (or force-push) command actually runs.
- **W2 — Review-cost scaling.** The minimum staffing for any code PR is 3 review agents, and
  re-review after an address round is implicitly a full re-run. Add a mechanical **light tier**
  for small no-risk diffs and a **delta-scoped re-review** rule.
- **W3 — Reviewer diversity.** All reviewers are the same model; parallel sampling gives
  variance but not decorrelated *bias*. Force search-path diversity via **lens assignment**,
  mechanize the **adversarial pass** for the cases where it pays, and add an opt-in
  **model-mix** knob.
- **W4 — Knowledge hygiene & onboarding.** Category boundaries are judgment calls, polluted
  entries compound in a committed store, and the 9-section interview is a heavy first touch.
  Add a **category test** table, **accept-time pointer verification**, a **misfile-move** rule,
  and a **quick setup** path for `/pm-loop-init`.

## 2. Non-goals

- **Not** abstracting away GitHub/`gh` (v1 decision D9 stands) and **not** revisiting
  squash-as-the-only-merge-style.
- **Not** adding real concurrency control (locking) for parallel PM sessions — the advisory
  live-session heuristics stay as-is.
- **Not** redesigning the knowledge taxonomy — the six categories and their stores are
  unchanged (existing consumer stores must stay compatible); we only make routing mechanical.
- **Not** turning the hook into a security boundary. It is defense-in-depth against process
  drift, not against a malicious model or user.

## 3. Locked decisions

Settled during brainstorming (2026-07-23):

| # | Decision | Rationale |
|---|---|---|
| D11 | **Guardrail = plugin-shipped `PreToolUse` hook** (`hooks/hooks.json` + script) that returns `permissionDecision: "ask"` on merge/force-push commands. | Ships and updates with the plugin; model-independent; fires at the exact moment of the irreversible act. Rejected: init-scaffolded permission rules (edits the user's settings, drifts from plugin updates); approval-marker files (the model writes the marker — circular trust). |
| D12 | **Hook scope-checks for `.claude/pm/profile.md` and exits silently when absent.** | Plugins are machine-global; the hook must not add prompts to repos that never opted into pm-loop. |
| D13 | **Hook fails open** (parse error → exit 0, warning on stderr) and is documented as defense-in-depth (regex matching; weakened under `bypassPermissions`). | A broken hook must not brick every Bash call. The prose gate remains the primary mechanism; the hook is the backstop. |
| D14 | **Light tier is mechanical and conjunctive** (no risk-class match AND small diff AND no sensitive content classes), generalizing the docs-only carve-out; **never applies where the operational-docs caveat applies**; single-reviewer escalation path back to baseline; profile opt-out, default on. | Keeps "never sized by feel": the cheap path exists only where every trigger for heavier review is mechanically absent, and it self-corrects when the one reviewer disagrees. |
| D15 | **Re-review after an address round is delta-scoped by default**, with mechanical triggers for a full re-run. | The current "Re-review." is ambiguous and reads as a full re-run — the single biggest recurring token cost in the loop. |
| D16 | **Lens = lead emphasis, not blinders.** Full-rubric duty and out-of-lens reporting obligations are explicitly unchanged. | Mitigates the responsibility-diffusion risk ("someone else's lens will catch it") that lens assignment introduces. |
| D17 | **Adversarial pass triggers narrowed + capped:** (a) initial review round of a PR whose tier yields ≥3 code-reviewers → one mandatory pass; (b) a blocker with cross-org severity disagreement, or a PM-proposed downgrade of a blocker → one pass before resolution. At most one pass per review round. | The earlier "any blocker" trigger double-pays: blockers already never auto-pass and get an address → re-review cycle. These two triggers are where refute-or-confirm has the highest value per token. |
| D18 | **Model mix is an opt-in optional profile section (`## Review diversity`).** Absent → all agents `inherit` (exactly today's behavior). Unavailable model → fall back to inherit and record in the run doc. Guidance: mix comparable-tier models. | The only true bias-decorrelation lever, but it costs money and interacts with the severity ladder (a noisy weak-model reviewer inflates severity via the disagreement-resolves-higher rule) — so it must never be the silent default. |
| D19 | **Pointer verification happens at accept time** (triage), not only at read time. A pointer resolves if the named file/symbol exists, **or** the named PR/issue exists; knowledge about removed/renamed things must point at the PR/issue that removed it. | Blocks the cheapest rot class (dangling references) once at write time instead of charging every future reader. Explicit limitation: verifies liveness, not truth — claim truth still rides the PR-review path. |
| D20 | **Quick setup presents one full profile draft with per-value provenance tags, and safety fields are never silently defaulted** — compliance mode and risk classes each get a mandatory one-line callout when left at a default. | One-shot confirm invites rubber-stamping; a wrong profile poisons every future run. Provenance + callouts keep the single round honest. |
| D21 | **Every prose addition in this design is mechanical in form** — a table, a one-liner, or a trigger condition — **and is pinned by `check.sh`** where a static check can hold it. | These changes add prose to a control plane whose length is itself weakness W1; mechanical form minimizes the judgment surface, and the gate prevents silent regression. |

## 4. W1 — Merge-gate hook

### 4.1 New file: `hooks/hooks.json`

Plugin hook manifest (same schema as settings hooks):

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "\"${CLAUDE_PLUGIN_ROOT}/scripts/merge-gate-hook.sh\"" }
        ]
      }
    ]
  }
}
```

### 4.2 New file: `scripts/merge-gate-hook.sh`

Behavior (stdin = the hook's tool-call JSON; python3 for JSON parsing — already a repo
prerequisite via `check.sh`):

1. **Scope check:** locate the repo root containing the CWD (`git rev-parse --show-toplevel`,
   falling back to the CWD outside a git repo); if `<root>/.claude/pm/profile.md` does not
   exist, exit 0 silently (not a pm-loop-managed repo — no opinion).
2. Parse `tool_input.command`. On any parse failure: warn on stderr, exit 0 (**fail open**, per D13).
3. If the command matches a **gated pattern**, emit
   `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "ask", "permissionDecisionReason": "pm-loop merge gate: <which pattern> — human approval required at execution time"}}`
   and exit 0. Otherwise exit 0 with no output.

Gated patterns (matched anywhere in the command string; false positives are acceptable — "ask"
merely prompts):

- `gh pr merge` (any flags),
- `gh api` whose arguments contain `pulls/<n>/merge`,
- `git push` carrying `--force`, `--force-with-lease`, or a standalone `-f` flag.

Not gated: branch deletion and other post-merge cleanup (routine, prompted-per-merge would be
noise), `git rebase` (local history work is legitimate in worktrees).

### 4.3 Doc changes

- `commands/pm-loop.md` step 6: one sentence after the merge command — the harness will prompt
  the human when the merge command runs; that prompt **is** the merge gate manifesting — never
  route around it (e.g. by switching to a raw API call that evades the pattern).
- `README.md`: new **Deterministic guardrails** section — what the hook gates, the
  double-confirm being intentional (chat approval is not machine-verifiable, so the harness
  prompt at execution time is the hard gate), the `bypassPermissions` caveat, the
  defense-in-depth disclaimer, and that non-pm-loop repos are unaffected.

### 4.4 Gate additions (`scripts/check.sh`)

- Required files += `hooks/hooks.json`, `scripts/merge-gate-hook.sh`.
- `hooks/hooks.json` parses as JSON and references `merge-gate-hook.sh`.
- `bash -n scripts/merge-gate-hook.sh` passes; the script is executable.

## 5. W2 — Light tier + delta-scoped re-review

### 5.1 Light tier (extends "Review tiers" in `skills/reviewing-prs/SKILL.md`)

A PR runs at the **light tier** only when **all** hold (mechanical, recorded in the run doc
with the measured numbers):

- no risk class matches the diff (neither path nor keyword signal);
- the diff is small: **≤ 50 changed lines** (additions + deletions) across **≤ 3 files**;
- no changes to dependency manifests, schema/migrations, auth/authz code, CI or tool config;
- the operational-docs caveat does not apply (that caveat always wins).

Staffing at the light tier: **1 code-reviewer** (full rubric, including basic security
detection), **security may skip** (recorded with why), **compliance per the profile's mode**,
unchanged.

**Escalation:** if the single reviewer files any blocker or major, or judges the light-tier
criteria misapplied, the PM re-runs the review at baseline (recorded).

**Profile opt-out:** an optional `Light tier: off` line in the profile's `## Risk classes`
section disables the tier (default: on). `templates/profile.md` gains the guided line.

### 5.2 Re-review scope (new `## Re-review scope` heading in `SKILL.md`)

After an address round, the default re-review is **delta-scoped**: verify each actionable
finding's resolution, and review only the diff between the previously reviewed head and the
new head (`git diff <reviewed-sha>...<new-head>`), dispatched to **one reviewer per org that
raised the addressed findings**. A **full re-review at the PR's original tier** is required
when any of these mechanical triggers holds:

- the address-round delta matches a risk class (path or keyword),
- the delta exceeds the light-tier size limits (> 50 changed lines or > 3 files),
- the address round changed files outside the scope of the findings being addressed.

The scope decision is recorded in the run doc. `commands/pm-loop.md` step 5's "Re-review."
becomes a pointer to this section.

### 5.3 Gate additions

- `require_heading` `SKILL.md` `'^## Re-review scope'`.
- `grep -F 'Light tier'` in both `SKILL.md` and `templates/profile.md`.
- `commands/pm-loop.md` references `Re-review scope`.

## 6. W3 — Reviewer diversity

### 6.1 Lens assignment (new `## Lens assignment` heading in `SKILL.md`; applied by `pr-reviewer`)

When the tier yields **N ≥ 2 code-reviewers**, the PM assigns reviewer *i* lens *i* from this
ordered list (cycling if N > 4), and passes the lens in the dispatch prompt:

1. correctness & edge cases
2. API contracts & cross-module consistency
3. test adequacy & spec fidelity
4. maintainability & conventions

A lens is a **lead emphasis, not blinders** (D16): the full rubric still applies to every
reviewer, and out-of-lens findings carry equal weight and equal reporting obligation. The PM
records the lens map in the run doc. `agents/pr-reviewer.md` gains a `## Lens assignment`
section stating how to apply an assigned lens without diluting full-rubric duty.

### 6.2 Adversarial pass (new `## Adversarial pass` heading in `SKILL.md`)

Replaces the discretionary "may run an adversarial round" sentence in `commands/pm-loop.md`
step 4 with a pointer to this mechanical rule. Triggers (D17):

- **(a)** the initial review round of any PR whose tier yields **≥ 3 code-reviewers** → one
  mandatory pass;
- **(b)** a **blocker** finding on which orgs disagree about severity, or which the PM proposes
  to downgrade → one pass before the severity is resolved (consistent with the existing
  no-unilateral-downgrade rule for security/compliance findings).

**Cap: at most one adversarial pass per review round.** The pass is one `pr-reviewer` instance
dispatched with the consolidated top findings and the mandate: *refute or confirm each, and
hunt for what every reviewer missed.* Its findings join the union under the normal severity
ladder. No new agent file.

### 6.3 Model mix (new optional profile section `## Review diversity`)

`templates/profile.md` gains a tenth section, **optional**:

- Per-org model overrides, e.g. `pr-reviewer: <model>` / `security-reviewer: <model>`;
  unlisted orgs (or an absent section) inherit the session model — exactly today's behavior.
- Guided warning: mix **comparable-tier** models — a noisy weaker-model reviewer inflates
  severity via the disagreement-resolves-higher rule.

PM dispatch rule (in `commands/pm-loop.md` step 4): when the profile names an override, pass
it as the subagent's model; if the model is unavailable or dispatch fails on it, **fall back to
inherit and record the fallback in the run doc**.

Consumer-facing docs: `README.md` profile table gains the row and "Nine sections" becomes
"Ten sections"; `commands/pm-loop-init.md` lists the section as optional and not interviewed
(guided placeholder only).

### 6.4 Gate additions

- `require_heading` `SKILL.md` `'^## Lens assignment'` and `'^## Adversarial pass'`.
- `require_heading` `agents/pr-reviewer.md` `'^## Lens assignment'`.
- Profile-template heading list += `'^## Review diversity'`.

## 7. W4 — Knowledge hygiene & onboarding

### 7.1 Category test (in `commands/pm-loop.md`, Knowledge step 2 triage)

A compact routing table — one discriminating question per category, labeled **Category test**
so the gate can pin it:

| category | one-question test |
|---|---|
| invariant | A fact about *this* codebase/system that must remain true (and code could silently violate)? |
| recurring-finding | A defect class a reviewer has filed (or would file) more than once? |
| gotcha | A surprising behavior of an external tool/system we must work around? |
| decision | A trade-off we chose among alternatives (and could reasonably revisit)? |
| domain | A market/regulatory/user fact that is true regardless of our code? |
| process | About how we work — workflow, review, tooling practice? |

Tie-breaker (one line): when two rows match, prefer the store an agent must **pre-read to
prevent a defect** (invariants / findings / gotchas) over the descriptive stores (decisions /
domain / team-learnings).

### 7.2 Verified pointer (accept rule, same triage step)

An accept rule labeled **Verified pointer** (so the gate can pin it): before accepting a
candidate, **resolve its pointer**: the named file/symbol exists (one
Glob/Grep), or the named PR/issue exists (`gh` view). Knowledge about something removed or
renamed must point at the PR/issue that removed it. An unresolvable pointer → correct it or
reject the candidate. Stated limitation (D19): this verifies **liveness, not truth** — claim
truth is still guaranteed by the knowledge-rides-its-PR review path.

### 7.3 Misfile move (curate step 5, one line)

When a triage touching a store's neighborhood notices a misfiled entry, move it to its correct
store in the same edit.

### 7.4 Quick setup (new `## Quick setup` heading in `commands/pm-loop-init.md`)

At the start of `/pm-loop-init`, offer two paths: the existing per-question **interview**, or
**quick setup**:

1. Gather signal (unchanged step 1) and fill a complete `profile.md` draft.
2. Present the entire draft in **one message**, with a provenance tag on every value —
   `(inferred)` or `(default)`.
3. **Safety fields are never silently defaulted** (D20): if compliance mode or risk classes are
   left at a default, the message must carry a one-line callout each — e.g. *"Compliance is
   `off` — change this if the project touches regulated domains"* / *"Risk classes are empty —
   declare classes if any change type deserves heavier review."*
4. One confirm-or-edit round, then scaffold (unchanged steps 3–5). Idempotency rules unchanged.

### 7.5 Gate additions

- `require_heading` `commands/pm-loop-init.md` `'^## Quick setup'`.
- `grep -F 'Category test'` and `grep -F 'Verified pointer'` in `commands/pm-loop.md`.

## 8. Token accounting (expected, per typical mixed run)

| Change | Delta |
|---|---|
| Merge-gate hook | ±0 loop tokens (shell script; one extra human prompt per merge) |
| Light tier | −2 review agents on every qualifying small PR |
| Delta-scoped re-review | large cut on every address round that doesn't trip a full-re-review trigger |
| Lens assignment | ~0 (a line or two per dispatch prompt) |
| Adversarial pass | +1 reviewer pass, only on ≥3-reviewer PRs or disputed/downgraded blockers |
| Model mix | 0 unless opted in |
| Pointer verification | +1 cheap lookup per knowledge candidate |
| Quick setup | fewer init round-trips |

Net: expected **decrease** for typical usage; increases are confined to high-risk PRs, where
they are the point.

## 9. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Hook evasion (rephrased commands) or `bypassPermissions` | Documented as defense-in-depth (D13); the prose gate remains primary; README caveat. |
| Hook prompting in unrelated repos | Profile-presence scope check (D12). |
| Hook bug bricking Bash calls | Fail-open + stderr warning (D13); `bash -n` in the gate. |
| Lens responsibility diffusion | D16 wording: full rubric mandatory, out-of-lens findings equal weight. |
| Weak-model reviewer noise inflating severity | Comparable-tier guidance in the profile section; fallback-and-record rule. |
| Light tier waving through a risky small diff | Conjunctive conditions include content classes (deps/schema/auth/CI); single-reviewer escalation; operational-docs caveat always wins; profile opt-out. |
| Quick-setup rubber-stamping | Provenance tags + mandatory safety-field callouts (D20). |
| This design itself grows the prose control plane | D21: mechanical form only; every addition pinned by `check.sh` where checkable. |

## 11. Acceptance

1. `scripts/check.sh` passes with all new checks in place.
2. Hook smoke test (no live session needed): pipe crafted hook JSON into the script —
   `gh pr merge 1 --squash` → `"ask"` output; `ls` → silent exit 0; same merge command with no
   `.claude/pm/profile.md` in CWD → silent exit 0; malformed JSON → stderr warning, exit 0.
3. Doc coherence: README table, `templates/profile.md`, and `pm-loop-init.md` agree on ten
   sections and on which are optional.
4. Existing consumer compatibility: a v0.1-initialized repo (nine-section profile, no
   `Light tier:` line) runs without modification — a nine-section profile stays valid (the
   tenth section is optional) and no model mix applies. The only intended behavior change for
   such repos is the new default staffing on qualifying small PRs (light tier on); a consumer
   that wants the old staffing adds `Light tier: off`.
